# Резервное копирование и восстановление

## Состав и согласованность

`begomctl backup run` открывает повторяемый SQL snapshot, получает готовый каталог, выполняет `pg_dump` с экспортированным snapshot, затем проверяет и упаковывает SQL, опубликованные видео, безопасные метаданные и sidecar публикации. Промежуточные файлы не входят. Манифест содержит версию приложения/схемы, роль владельца, ID тома, SHA-256 дампа и каждого файла. Неподтверждённые результаты после восстановления будут выполнены повторно.

Набор передаётся в зашифрованный restic. Повреждение/исчезновение готового файла или потеря mount прерывает создание набора; успешный статус не записывается. Копирование не блокирует появление новых публикаций: они относятся к следующему snapshot. Для копии используют отдельную роль SQL только для чтения и идентичность NAS с чтением опубликованных файлов.

Runtime-секреты, данные OpenBao/KDC и приватные ключи **не включаются** в пользовательский архив restic автоматически. Сохраните их отдельной защищённой процедурой, иначе восстановленный SQL не восстановит ключ шифрования URL, доверие агентов и учётные данные. Сохраняйте provisioning bundle, OpenBao raft/recovery material, KDC database/stash/keytabs, CA, ключ подписи пакетов и пароль restic на независимых носителях. Разделите доступ хранителей к ключам и копиям.

## Локальный профиль

```sh
docker compose --profile backup build backup
docker compose --profile backup run --rm backup backup init --config /config/backup.json
docker compose --profile backup run --rm backup backup run --config /config/backup.json
```

`init` нужен только для новой репозитории. Не повторяйте его для исправления недоступной либо повреждённой копии. Результат `run` содержит snapshot ID, времена и число файлов. Пароль и DSN берутся из файлов и не печатаются. Пароль SQL передаётся `pg_dump/pg_restore` через закрытый временный pgpass, а не в argv.

Именованный том `backup-repository` на том же хосте проверяет процедуру разработки. Он не защищает от потери этого хоста. Linux-профиль запускает таймер на независимом узле, проверяет отдельный mount и читает NFS с Kerberos от имени backup principal. Репозиторий должен физически находиться вне основного NAS/SQL-узла.

## Изолированное восстановление

Прежде чем восстанавливать службу, проверьте копию на отдельном стенде с закрытой исходящей сетью и отключёнными агентами. Выберите явный snapshot и **новые** каталог и БД с префиксом `begom_restore_`. Конфигурация восстановления содержит административный SQL-доступ в закрытом файле, путь restic и пароль; необходимые роли заранее создаются, их секреты берутся из защищённой копии.

```sh
bin/begomctl restore --config /secure/restore.json --snapshot SNAPSHOT_ID --target /srv/restore/NEW_SET --database begom_restore_NEW_SET
```

Нужны `restic`, `pg_restore` версии PostgreSQL 18 и доступ к выбранной SQL-инстанции; контейнер `begom-backup:1.0.0` уже содержит инструменты. Новый каталог создаётся закрытым, небезопасные пути и symlink в архиве запрещены. Перед импортом проверяются версия схемы, весь манифест, размеры и SHA-256 SQL/видео/sidecar. Существующая БД или каталог не перезаписываются. Роль владельца таблиц восстанавливается явно, чтобы будущие миграции не потеряли право DDL.

Результат содержит измеренные RPO (возраст snapshot) и RTO (продолжительность процедуры). После восстановления требуется отдельно проверить доступы, mount, ключ шифрования метаданных и выборочную выдачу через NGINX. Файл `restore-isolated.json` напоминает, что копия ещё не является рабочей службой. Восстановленные файлы закрыты режимом 0600; до запуска восстановленного публикатора/веб-шлюза установите владельца publisher, группу media и права 0750/0640 только на проверенный каталог published. Отделите marker нового тома от исходного стенда; настройте согласованную идентичность тома.

Сначала запускайте только SQL и проверку данных, затем OpenBao и координатор; после проверки drain и ACL подключайте агенты. До открытия выдачи проверьте отрицательные попытки доступа. Переключение production на восстановленный стенд — отдельная операционная процедура владельца. Автоматического удаления исходной БД или данных в `restore` нет.

## Проверка процедуры

```sh
python3 tests/backup/run.py --state .local --output artifacts/backup
```

Программа работает только с сгенерированным mock-профилем, создаёт новую БД/каталог, сохраняет фактический протокол и оставляет восстановленный набор для проверки. При отдельном имени Compose задайте те же `COMPOSE_PROJECT_NAME` и `BEGOM_STATE_DIR`. Независимое восстановление Linux-стенда и локальный прогон фиксируются раздельно. Retention/`restic forget --prune` намеренно не запускаются автоматически: удаление копий требует отдельной политики владельца.
