# Обновление и обслуживание

## Поставка

Сохраните проверенную резервную копию и текущие версии образов/бинарников. Выполните мягкую паузу заданий, дождитесь отсутствия активных публикаций, проверьте mount, SQL и OpenBao. Соберите кандидат, выполните `make check`, интеграционные и стендовые проверки согласно [программе](testing.md). Новые SQL-изменения оформляются новой миграцией; существующие checksum не меняются.

В Compose пересоберите приложение и запустите `docker compose up -d --build`. Именованные тома и каталог профиля сохраняются. При перезапуске OpenBao выполните unseal. Дождитесь `readyz`, регистрации трёх агентов и свежих метрик, затем возобновите задания. Изменение источника требует новой БД и профиля. Новое значение глобальной квоты также требует перезапуска координатора с защитным drain.

В Linux заменяйте бинарник координатора атомарно, затем перезапускайте `begom-coordinator`. Агент обновляется подписанным пакетом. API первой поставки требует одинаковую версию координатора и агента, поэтому на время смены версии работа приостанавливается. Не включайте одновременно два активных координатора как способ обновления.

Пакет агента создаётся на доверенном сборочном узле:

```sh
bin/begomctl package --agent bin/agent --key /secure/begom-bundle/bootstrap/package.key --output /secure/packages --version 1.0.0
```

Перенесите `.json` и `.tgz` в каталог пакетов координатора, доступный ему только для чтения (`.local/packages` либо `/var/lib/begom/packages`). Запустите `update` с этой версией из интерфейса/CLI. Помощник проверяет подпись Ed25519 над версией, размером и SHA-256, единственную обычную запись `agent`, лимит архива и путь. Бинарник fsync, каталог версии и ссылка `current` публикуются атомарно. Повтор разрешён только при совпадении существующего исполняемого файла с проверенным пакетом. Произвольные install-скрипты отсутствуют.

После обновления проверьте версию, heartbeat, пробное задание и журнал worker_actions. При `outcome_unknown` сначала получите status. Для отката используйте ранее проверенный совместимый подписанный пакет. Если схема БД несовместима со старым координатором, используйте изолированное восстановление целой копии; не выполняйте частичный SQL downgrade.

## Сертификаты и секреты

Runtime mTLS-идентичности выдаются на 48 часов. Координатор обновляет их через OpenBao при приближении срока; агент и сервер перечитывают идентичности. AppRole token живёт ограниченное время, секреты кэшируются до минуты. Для ручной ротации агента администратор вызывает certificates/rotate; для немедленного отзыва — certificates/revoke с serial. Отзыв текущего сертификата прекращает также control и метрики; сначала обеспечьте получение новой идентичности либо восстановительный доступ узла.

Сертификаты веб-шлюза, SQL, OpenBao и сборщика метрик выдаются на 90 дней. Их обновляет оператор до истечения:

```sh
bin/begomctl renew-leaf --dir .local --name web
```

Допустимые имена — существующие управляемые идентичности профиля. Команду выполняют с доступом к закрытому CA и целевым файлам; после локального переназначения UID для этого может потребоваться корневой provisioning-контейнер. `renew-leaf` сохраняет SAN, URI, CA и права файла. Для NGINX выполните reload, для PostgreSQL reload/перезапуск по его эксплуатационным правилам, для OpenBao согласованный restart/unseal. В Linux перенесите обновлённые leaf-файлы по их действующим путям и владельцам. Не заменяйте CA новым `init` поверх рабочего профиля.

CA первой поставки действует год. Планируйте его согласованную замену с распространением доверия и выпуском всех идентичностей; бесшовная смена корня доверия с двумя CA не автоматизирована. Отдельно защищайте CA key, ключ подписи пакетов, Kerberos master/keytabs, OpenBao recovery shares и пароль restic. Секреты БД меняются одновременно в PostgreSQL и соответствующих KV-профилях OpenBao; после проверки обновления завершите старые подключения. Не вводите секреты в URL интерфейса или логи.

## Хранилище и журналы

Необходимый свободный объём учитывает две копии активной загрузки, опубликованные файлы и SQL-резервы. Отказ mount либо неверный `.begom-volume` прекращает выдачу и работу. Не создавайте локальный каталог вместо утраченного NFS. После восстановления проверьте `findmnt`, `sec=krb5p`, Kerberos tickets, UID/GID, доступ издателя и отрицательные проверки агентов/веб-шлюза.

Публикатор восстанавливает незавершённые стадии и проверяет наличие/размер готовых записей. Фоновая проверка SHA-256 идёт ограниченными порциями; повреждённые записи изымаются и перемещаются в карантин. Лишняя копия, проигравшая каноническую дедупликацию, удаляется по подтверждённой SQL-публикации; очистка восстанавливается после сбоя. Неизвестные старые временные каталоги не удаляются автоматически. Перед ручным удалением остановите соответствующий агент и убедитесь по SQL, что attempt не действует, публикация не verifying и готовый файл не ссылается на каталог. Карантин сначала исследуют либо копируют; он не является резервной копией.

Fluent Bit имеет ограниченный файловый буфер 512 МиБ на выход и ограничение памяти. Docker отправляет только журналы контейнеров Begom через локальный Forward с ограниченной очередью; доступ ко всем логам Docker хоста не требуется. При длительной недоступности Loki буфер может достигнуть предела; следите за drops/retries и предупреждением. Loki хранит 14 дней; Prometheus также ограничен временем/объёмом. SQL-события и аудит не очищаются автоматически: срок хранения и архивирование задаются оператором с учётом требований владельца.

Глобальная Grafana предназначена администратору. Показатели заданий в приложении фильтруются по ACL. Не публикуйте Prometheus, Loki, Forward, PostgreSQL и mTLS API в общедоступную сеть.
