# ADR-0001. Профиль реализации Begom на Go

Дата: 23 октября 2026 года. Статус: реализация согласованного владельцем плана. Основание — запрос «PLEASE IMPLEMENT THIS PLAN» и предшествующие уточнения владельца. Документ не утверждает прохождение физического стенда.

## Решение

Прикладные процессы реализуются на Go 1.26 с `net/http`, `pgx`, PostgreSQL 18 и версионированным JSON API. Координатор объединяет C1–C10, включая диспетчер C6 и издателя; агенты выполняют A1–A5. Разделение модулей на схеме не требует отдельных процессов. Очередь блоков, подтверждения и идемпотентные ответы хранятся в SQL. Очереди HTTP-допусков находятся в памяти одного активного C6. Redis, брокер и отдельный сервер видеопотока не добавляются.

Доступ к видео проходит через локальные учётные записи, роли и ACL заданий. NGINX выдаёт только опубликованные файлы после `X-Accel-Redirect` от координатора. OpenBao хранит рабочие ключи, параметры соединения, ключ шифрования метаданных и SSH-идентичности. Терминал включён и использует закрытый набор команд.

Для Kinescope сохраняется числовой перебор ТЗ. Перенаправление может привести на короткий идентификатор либо UUID, который хранится отдельно. Указанный владельцем UUID-URL служит образцом страницы, а не заменой числового диапазона. Без публичного разрешения скачивания результат — `skipped`. Административный API Kinescope и HLS/DASH для получения видео не используются.

§24 ТЗ исключён по явному решению владельца. Локальный Compose использует общий каталог разработки; профиль реальных серверов сохраняет NAS/NFSv4 `krb5p`, отдельные идентичности и независимый узел копирования.

## Уточнения реализации

- Файл агента копируется в закрытую область издателя, проверяется и атомарно публикуется. Это сохраняет инвариант ЭП/ТП: агент не может менять опубликованный inode через оставшийся открытым дескриптор. Резерв SQL учитывает обе копии. Подтверждённая временная область затем удаляется.
- C6 имеет отдельный небольшой пул SQL для проверок. Транзакционный обработчик пользуется своим соединением, не получает второе из занятого пула. Это устраняет выявленную нагрузочным прогоном взаимную блокировку.
- Снижение нагрузки, `Retry-After` и максимальный горизонт квоты сохраняются в SQL. Защитный интервал нового поколения учитывает этот горизонт и старые соединения. Очень низкие лимиты могут увеличивать время готовности после рестарта.
- ECDSA P-256 используется для X.509: подпись CA совместима с SCRAM channel binding PostgreSQL, а серверный ключ — с браузерами. Ed25519 остаётся алгоритмом SSH и подписи пакетов агента.
- Каталог NAS задаётся при установке узла и отображается в инвентаре. Изменение пути требует отключения узла, смены проверенного mount и новой регистрации; произвольный путь в отчёте агента не принимается.
- Смена донора требует отдельной БД. `system_profile` предотвращает смешивание числовых идентификаторов mock и Kinescope.

- Управление агентом в Linux использует отдельный экземпляр OpenSSH на приватном порту 2222. Штатная SSH-идентичность установки не заменяется, чтобы не разрывать Ansible-доступ; ключ управляющего пользователя содержит принудительную команду.

## Последствия и совместимость

Один активный координатор ограничивает доступность контрольной плоскости; SQL и NAS должны быть восстановлены до продолжения. Подтверждённые файлы не требуют повторного скачивания. Старые попытки не получают право публикации. При потере SQL, разрешения, сессии, mount или доступности секретов зависимые операции прекращаются.

Профиль первой поставки использует API `1`, приложение `1.0.0` и миграции `001–004`. Все изменения схемы добавляются новой миграцией. Изменение формата, длительности допусков или алгоритма квоты в будущей поставке требует проверки совместимости и сохранения защитного интервала предыдущего поколения.
