## Не выполнено на целевом оборудовании

Три независимых Ubuntu 24.04 сервера, настоящий NAS/NFSv4 `krb5p`, отрицательные права Kerberos, отказ NFS/KDC/сети и восстановление на физически независимом backup-узле требуют адресов и подготовленного оборудования. Подготовлены установка, отдельный negative playbook и Ansible-драйвер; локальные контейнеры не выдаются за прохождение этих испытаний.

Не измерялись десятки агентов, многодневный проход, одновременные многогигабайтные файлы и предельная пропускная способность NAS. Нагрузочный протокол относится к синтетическим небольшим видео и указанной задержке mock. Файлы большого размера обрабатываются потоково, но это не заменяет измерения на целевом диске/сети.

Kinescope проверялся по публичному формату страницы и опубликованному клиентскому контракту downloadLink. Данный владельцем UUID-образец не публиковал разрешение скачивания и соответствует skipped. Реальное разрешённое скачивание Kinescope и его квота не измерялись; 1 RPS является исходной настройкой Begom. Обход ограничений не реализован.

Первый [PR-прогон GitHub Actions](https://github.com/lord-laminat/Begom/actions/runs/39930726635) завершился ошибкой: задание `go` прошло все шаги, а `stand` остановилось при создании контейнера из-за неподдерживаемого параметра `fluentd-write-timeout`. Приёмочные шаги этого прогона не выполнялись. В Compose и шаблоне Linux-профиля параметр заменён ограниченным режимом `non-blocking`; CI сохраняет версии Docker и диагностические журналы при сбое. Исправление локально проверено через `docker compose config --quiet`, рендеринг 12 шаблонов, syntax-check Ansible и запуск одноразового контейнера с параметрами журналирования из Compose. Результаты последующих удалённых прогонов следует смотреть в PR отдельно от приведённых локальных команд. Автоматизация корневой смены CA и удаление старых копий/неизвестных staging-каталогов не выполняются: процедуры описаны в эксплуатационных руководствах.

В [повторном PR-прогоне](https://github.com/lord-laminat/Begom/actions/runs/39932698230) на Docker 28.0.4 прошли `go`, запуск стенда, измеряемая приёмка (104 одновременных запроса, 43 поступления за секунду, перевыдача за 10.787 с) и 18 браузерных проверок (максимальная задержка метрик 2938 мс). Отказной набор остановился на `load_started`: предшествующая остановка запроса учитывалась как сетевая ошибка и снижала адаптивный множитель. Воспроизведение на локальном стенде подтвердило множитель `0.1` после остановки нагрузки. C6 теперь освобождает прерванные запросы утратившей право работы попытки без дополнительного снижения квоты, сохраняя адаптацию для настоящих сетевых ошибок и ответов донора. Это покрыто SQL-регрессией; повторные `make check` и `make integration` прошли. Отказной драйвер задаёт независимый mock-сценарий с задержкой 12 секунд и прежним критерием 40 одновременных запросов; накопленное SQL-состояние квоты сохраняется. CI использует Bash с `pipefail`, чтобы ошибка ENOSPC-теста не скрывалась командой `tee`.

Локальный отказной прогон также выявил конфликт условий самого теста: автоматическая остановка после 30 секунд без агентов могла сработать во время намеренной недоступности OpenBao. Для тестового задания задан предел 180 секунд и добавлена обязательная проверка возобновления обработки после unseal; производственные значения по умолчанию не меняются. Протокол отказного драйвера содержит общий результат и тип исключения, чтобы ошибка после успешно выполненных промежуточных проверок не выглядела успешным прогоном.

Первый запуск профиля Kinescope выявил гонку OpenBao: `unseal` завершился до готовности Raft к записи, и создание `secret/` было отклонено с `cannot write to readonly storage`. Bootstrap теперь до одной минуты ожидает активное состояние через `/v1/sys/health`, сохраняя прежние ключи и продолжая частичную настройку. Регрессии проверяют standby, восстановление и тайм-аут без записи; `make check` прошёл. На свежем OpenBao 2.7.1 первый bootstrap завершился за 8.343 с, повторный — за 0.022 с без изменения ключей. Действующий Kinescope-профиль восстановлен: HTTPS readiness и вход успешны, три агента онлайн, mock-донор отсутствует. Задания на внешний сервис для этой проверки не создавались. Отдельный [протокол](reports/2026-10-23-bootstrap.json) содержит параметры и хеши исходников.

Для bootstrap-исправления `cd46a1f` полностью прошли [PR-прогон](https://github.com/lord-laminat/Begom/actions/runs/39944591260) и [push-прогон](https://github.com/lord-laminat/Begom/actions/runs/39944587445): в каждом успешны `go` и `stand`, включая браузер, отказы, ENOSPC и восстановление копии.

Проверка Grafana на действующем Kinescope-стенде выявила стандартную домашнюю страницу вместо панели Begom и OOM при лимите 384 МиБ (событие Docker `oom`, завершение 137). В обоих профилях панель назначена домашней, ссылка ведёт к её UID, лимит памяти Grafana увеличен до 1 ГиБ. Запрос панели журналов использует метку `service`, общую для локального и Linux-профиля. Chromium 141 открыл домашнюю и сохранённую панели; доступны восемь панелей, 11 здоровых целей Prometheus и записи Loki. В результаты добавлена ссылка «Скачать» через существующий API с проверкой ACL; API и схема БД не менялись. Руководство описывает учётную запись клиента, доступ к заданию и сетевой адрес. В [локальном протоколе](reports/2026-10-23-observability-client.json) отдельно отмечено отсутствие скачанного Kinescope-файла для проверки клиентской выдачи. Проверка скачивания, SHA-256, Range и ACL добавлена в браузерный набор CI с тестовым донором; её наличие само по себе не является результатом запуска.

Первый [CI-прогон новых проверок Grafana](https://github.com/lord-laminat/Begom/actions/runs/39950045518) прошёл Go/SQL и приёмку, но остановился на запуске Grafana в Chromium Headless Shell. Локальное воспроизведение выявило наследуемую локаль `en-US@posix`, непригодную для `Intl.NumberFormat`. Контексты теста теперь задают `ru-RU`; локально те же панели успешно открылись в Headless Shell с Prometheus и Loki. При сбое сохраняются текст страницы, снимок и ошибки консоли; проверка видимости панели и тайм-аут не ослаблены.

## Вклад и воспроизводимость

Существенная часть исходного кода, конфигураций, тестов и новых документов создана Codex по ТЗ/ЭП/ТП и принятому плану.
